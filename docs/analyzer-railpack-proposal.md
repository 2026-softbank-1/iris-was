# AI Analyzer의 필요성과 Railpack 역할 및 승인 후 배포 제안

2026-10-02. 현겸님과 지민님 검토용 설계 제안. 이 PR은 문서만 추가하며 API나 Worker의 실행 동작을 변경하지 않는다.

## 제안 요약

저장소를 AI Analyzer Agent로 분석해 서비스 구성과 배포 스택·설정을 제안한다. WAS는 근거와 미확정 항목을 프론트에 응답한다. 사용자가 계획을 검토하고 승인 API를 호출하면 WAS가 권한과 계획 버전을 검증한 뒤 빌드 작업을 접수한다. Build Worker는 확정한 Dockerfile 또는 Railpack으로 이미지를 만들고, Deploy Worker가 해당 이미지 digest를 배포한다.

Analyzer는 빌더를 대체하지 않는다. Railpack의 빌드 분석을 활용하면서, 이미지 생성만으로 결정할 수 없는 앱 전체의 배포 조건을 검토 가능한 계획으로 만든다.

## Railpack이 실제로 하는 일

Railpack Core는 앱을 분석해 JSON 빌드 계획을 생성한다. 언어별 provider가 파일과 설정을 감지하고 빌드 단계를 구성한다. BuildKit은 그 계획으로 이미지를 만든다. 계획에는 빌드 단계·캐시·Secret 이름·컨테이너 시작 명령·환경변수도 들어간다. 따라서 Railpack을 단순 컴파일 도구로 설명하거나 환경변수를 전혀 다루지 못한다고 설명하면 부정확하다. [공식 아키텍처](https://railpack.com/architecture/overview/).

자동 감지 결과는 설정 파일과 환경변수로 조정할 수 있다. 비표준 앱도 설정을 통해 빌드할 수 있으므로 특정 구조를 감지하지 못했다고 곧바로 빌드 불가능으로 판정하지 않는다. [설정 파일](https://railpack.com/config/file/).

## Railpack만으로 해결되지 않는 기술적 범위

아래 한계는 공식 문서의 빌드 계획 범위에서 도출한 역할 경계다. Railway 플랫폼 전체의 기능 부재를 뜻하지 않는다.

| 배포에서 결정할 문제 | Railpack의 범위와 한계 | Analyzer와 WAS가 보완할 내용 |
|---|---|---|
| 실행 단위와 서비스 연결 | 빌드 대상의 provider와 명령을 감지하지만, 이미지 빌드 계획만으로 앱 전체의 운영 연결이 확정되지는 않음 | 코드 모듈과 실행 단위를 구분하고 Web/API/DB 의존 관계, 서비스별 root·포트·연결 설정을 제안 |
| 환경변수와 Secret 연결 | 빌드 Secret과 시작 환경변수를 다룰 수 있으나 실제 운영 Secret의 존재·권한·대상별 연결은 플랫폼 검증이 필요 | 키의 소비 서비스, build/runtime 단계, 필수 여부와 근거를 분석. 값은 추측하지 않고 WAS에서 입력 또는 Secret 참조 확인 |
| 클라우드와 운영 사양 | 이미지 생성 계획은 EKS 배치, IAM·Ingress·스토리지, 비용·가용성 계획의 승인 계약이 아님 | 지원 대상과 사용자 조건을 받아 스택·자원·네트워크를 제안. 측정값·가정·미확정 비용을 구분 |
| 사용자 승인과 변경 통제 | 빌드 계획 생성은 사용자가 이 소스와 운영 설정의 실행을 승인했다는 증거가 아님 | 고정 커밋·계획 버전·설정·타깃에 대한 승인 기록을 저장하고 Worker에서 재검증 |
| 실제 서비스 정상 동작 | 이미지 생성 성공만으로 DB 접근, API 연결, 기능 정상 동작이 입증되지는 않음 | 빌드와 배포 및 런타임 검사 결과를 별도 상태로 보관. 실패 시 실제 로그로 진단 |

Railway는 JS 모노레포의 배포 가능한 패키지 자동 감지와 서비스별 설정을 이미 지원한다. “Railpack 또는 Railway가 모노레포를 지원하지 못한다”는 주장을 하지 않는다. 우리의 필요성은 플랫폼에 넘길 서비스 관계·근거·운영 조건·승인 계약에 있다. [Railway 모노레포 지원](https://docs.railway.com/deployments/monorepo).

## Analyzer가 제안할 내용

- 서비스 역할·root·런타임·빌드 및 시작 명령·포트·상태 검사와 코드 근거.
- Web/API 연결, DB·스토리지 의존성, 환경변수 소비 위치와 build/runtime 구분.
- 지원하는 배포 타깃, 운영 조건과 자원·네트워크·Secret 바인딩 계획.
- 기존 Dockerfile 사용 또는 Railpack 빌드 선택. Dockerfile 부재 자체는 오류가 아니다.
- 확정 관측값과 추천·가정·질문을 구분한 응답. 불명확한 사항을 AI 확신만으로 확정하지 않는다.

분석 완료는 빌드 성공이나 실행 승인을 의미하지 않는다. AI는 제한된 제안을 반환하고 플랫폼 검증 코드가 실행 적합성을 판단한다. 자원·최대 처리량·총비용은 소스만으로 확정하지 않는다. GKE 등 미지원 타깃은 지원 완료로 표시하지 않는다.

## 승인 후 실행 순서

```text
고정 저장소 커밋으로 분석 작업 접수
  → Analyzer가 서비스 구조와 배포 스택·설정 제안
  → WAS가 계획·근거·확인 필요 항목 응답
  → 사용자 설정 보완 및 계획 재검토
  → 승인 API 호출
  → WAS가 소유자 권한·소스·최신 계획·필수 바인딩 검증
  → 승인한 계획으로 BUILD Job 접수
       ├ 선택한 기존 Dockerfile로 이미지 빌드
       └ Dockerfile이 없거나 Railpack을 선택한 경우 Railpack 빌드
  → ECR 이미지 digest 기록
  → DEPLOY Job으로 GitOps 갱신 및 Argo 배포
  → 실제 배포 상태와 검사 결과 응답
```

Control API는 승인과 DB/큐 기록을 담당한다. 모델 호출·CodeBuild·ECR·GitOps·Argo 작업은 Worker가 실행한다. Dockerfile과 Railpack은 이미지 빌드 경로이며 실제 배포는 Deploy Worker가 담당한다. 빌드 실패를 이유로 승인받지 않은 builder나 설정으로 자동 변경하지 않는다.

## WAS 응답과 승인 계약 논의안

아래 필드는 제안이며 현행 API로 구현된 계약이 아니다. 최종 endpoint와 필드명은 지민님·현겸님과 합의하고 OpenAPI에 반영한다.

| 응답 영역 | 프론트에서 필요한 정보 |
|---|---|
| 작업 상태 | 작업 ID, 분석·입력 대기·계획 검토·빌드·배포·실패 구분 |
| 소스와 계획 | 고정 커밋, snapshot 식별자, plan revision 및 digest |
| 분석 결과 | 서비스별 설정, detected/suggested/unknown, 코드 근거 |
| 배포 제안 | 지원 스택과 타깃, builder, 서비스 설정, 일반 환경값 또는 Secret 참조 |
| 승인 가능 여부 | 필수 질문, 차단 이유, 검토할 추천 및 가정 |
| 실행 결과 | 빌드·배포 ID, image digest, 실제 상태와 실패 진단 참조 |

WAS의 공통 `ApiResponse[T]` 봉투를 사용하고 기존 API 네이밍 규칙을 따른다. Agent 내부 JSON과 프론트용 응답을 무조건 동일하게 만들지는 않는다. 원본 근거와 미확정 상태는 변환 중에도 보존한다.

승인 요청은 적용할 source commit과 계획 버전을 지정한다. WAS는 요청자가 해당 서비스를 실행할 권한이 있는지, 계획이 최신인지, 필수 입력과 지원 조건을 충족하는지 검사한다. 승인 후 소스·설정·타깃이 바뀌면 이전 승인을 재사용하지 않고 새 계획을 승인받는다. 중복 승인 요청은 동일 실행으로 처리하며 Worker도 승인 기록과 계획 digest를 검사한다.

Secret 값은 분석 결과·PR·일반 API 로그에 넣지 않는다. 계획 단계에서는 참조와 연결 상태를 다루고 실제 값 공급은 해당 실행 단계의 권한을 가진 구성요소가 담당한다.

## 현재 구현과 이번 제안의 차이

[기존 통합 PR #9](https://github.com/2026-softbank-1/iris-was/pull/9)은 분석→입력 확인→계획→빌드→배포·실패 진단을 연결한다. 그 문서의 `autoDeploy:true` 경로는 최초 Analyze & deploy 요청을 실행 허용으로 사용하며 계획 생성 후 별도 승인 API를 기다리는 구조로 설명되어 있지 않다.

이번 제안은 **계획을 보여준 뒤 별도 API 승인을 받아 빌드·배포를 시작하는 구조**다. 기존 분석 결과 확인 API가 있다 해도 이를 배포 계획 승인과 동일하게 취급하지 않는다. 승인 상태·요청·기록·Job 생성 조건·프론트 화면에 대한 추가 구현 및 검증이 필요하다. 이 문서 PR은 그 구현을 완료했다고 주장하지 않는다.

## 현겸님과 지민님께 요청할 검토

- 현겸님: Analyzer 출력에서 builder/root/명령/포트/환경 바인딩을 Build Worker로 넘기는 계약과 승인 후 Job 접수 경계를 검토한다.
- 지민님·현겸님: 분석·계획 조회 응답, 질문 답변 및 계획 수정, 명시적 승인 API의 요청·응답을 합의한다.
- 공통: 기존 자동 배포 및 GitHub push 흐름에 별도 승인을 요구할지, 사전 승인 정책을 지원할지 결정한다. 무인 자동 배포에 대화형 승인을 무조건 적용하지 않는다.
- 공통: 오래된 계획 거절·중복 승인·소스 변경·필수 Secret 누락·미지원 타깃과 빌드 실패를 검증할 기준을 정한다.

완료 기준은 “계획 조회만으로는 빌드가 시작되지 않고, 유효한 승인 후 승인된 소스·설정으로 한 번의 논리적 실행이 생성되며, 변경된 계획은 재승인을 요구하는 것”이다.
