# 0018. CLI 로그인은 DB 세션 테이블과 폴링으로 하고 토큰은 한 번만 내준다

- 상태: 수락됨
- 날짜: 2026-10-03
- 결정자: 김지민

## 배경
`likelion login` 은 CLI 가 시작하고 사용자가 브라우저에서 GitHub 로그인을 승인한다. 승인이 끝나면 CLI 가 세션 토큰을 받아 `Authorization: Bearer` 로 쓴다. 서버가 지켜야 할 요청·응답 계약은 iris-cli 레포의 `docs/login-contract.md` 다.

[ADR 0003](0003-session-and-token-handling.md) 에 따라 세션은 서명된 JWT 이고 GitHub 사용자 토큰은 저장하지 않는다. 그런데 CLI 로그인은 "브라우저에서 일어난 승인"을 "CLI 프로세스"로 전달해야 해서, 둘 사이에 잠깐 상태를 들고 있을 곳이 필요하다.

## 검토한 선택지

흐름
1. **CLI 로컬 서버가 콜백을 받는다(loopback redirect).** 서버 저장소가 필요 없다. 하지만 원격·SSH·컨테이너 환경에서는 브라우저가 CLI 의 로컬 포트에 닿지 않고, GitHub App 의 Callback URL 을 CLI 포트에 맞춰야 한다.
2. **CLI 가 GitHub Device Flow 를 직접 쓴다.** 서버 상태가 없다. 하지만 CLI 가 GitHub 사용자 토큰을 쥐게 되고, 서버가 세션을 발급하는 ADR 0003 의 구조와 달라진다.
3. **서버가 대기 중인 로그인 세션을 저장하고 CLI 가 폴링한다.** 서버 상태가 늘지만 기존 웹 로그인 콜백과 세션 발급을 그대로 재사용한다.

저장 방식(3 을 고른 뒤)
- **A. 서명된 토큰만 쓰고 저장하지 않는다.** 서명된 세션 ID 로는 "한 번만 내주기", "거절", "승인 여부"를 표현할 수 없다. 상태가 필요하다.
- **B. 프로세스 메모리.** replica 가 여럿이고 재시작·배포로 사라진다. 승인 콜백과 폴링이 다른 Pod 로 가면 실패한다.
- **C. Redis 등 별도 저장소.** 이 서비스에는 PostgreSQL 만 있다. 만료 TTL 은 편하지만 인프라를 새로 들여야 한다.
- **D. PostgreSQL 테이블.** 이미 있는 저장소이고, 행 잠금으로 상태 전이를 직렬화할 수 있다. 만료는 시각 컬럼으로 처리한다.

## 결정
흐름은 3, 저장은 D 로 한다.

- 테이블 `cli_login_sessions`: `public_id`(인증 URL 에 들어가는 추측 불가한 값), `poll_secret_hash`, `status`(PENDING·APPROVED·DENIED·EXPIRED), `user_id`, `expires_at`, `consumed_at`, `last_polled_at`.
- **공개 ID 와 폴링 비밀을 분리한다.** 공개 ID 는 브라우저로 열리는 주소에 들어가고 로그에 남을 수 있다. 폴링 비밀은 CLI 만 알고 요청 본문으로만 보낸다. 둘 다 `secrets.token_urlsafe(32)`(256비트)다.
- **폴링 비밀은 해시로만 저장하고 상수 시간으로 비교한다.** 256비트 무작위 값이라 무차별 대입이 불가능하므로 느린 해시나 salt 없이 SHA-256 으로 충분하다. 비교는 `hmac.compare_digest` 로 한다.
- **토큰은 DB 에 저장하지 않는다.** 폴링이 `APPROVED` 를 처음 볼 때 세션 JWT 를 만들어 응답하고, 같은 트랜잭션에서 `consumed_at` 을 기록하며 상태를 `EXPIRED` 로 바꾼다. 같은 세션을 다시 폴링하면 `EXPIRED` 다. 승인·폴링은 `SELECT … FOR UPDATE` 로 행을 잠그고 읽어, 동시에 폴링해도 토큰은 한 번만 나간다.
- **만료는 10분**이다. 만료는 읽을 때 `expires_at` 으로 판단하고, 폴링이 만료를 보면 `EXPIRED` 로 저장한다. 승인 콜백이 만료된 세션을 만나면 승인하지 않고 404 로 답한다. 만료된 지 하루가 지난 행은 새 세션을 만들 때 지운다(인증 없이 만들 수 있는 엔드포인트라 행이 쌓이지 않게 한다).
- **같은 OAuth 콜백을 쓰고 state 의 목적으로 가른다.** state JWT 의 `purpose` 가 웹 로그인은 `oauth_state`, CLI 승인은 `cli_oauth_state` 이고 후자는 세션 공개 ID 를 싣는다. 목적이 달라 서로의 state 를 대신할 수 없다. nonce 쿠키는 그대로 써서, 승인하는 브라우저가 로그인을 시작한 브라우저와 같은지 확인한다. CLI 승인은 웹 세션 쿠키를 만들지 않고 세션만 승인한다(사용자·GitHub App 설치 동기화는 웹 로그인과 같다). GitHub 에서 승인을 취소하면 세션을 `DENIED` 로 바꾸고 안내 화면을 보여 준다.
- **폴링 빈도는 `PENDING` 응답에만 제한한다.** 직전 폴링으로부터 `interval`(2초)에서 0.5초를 뺀 시간보다 빠르면 `429` 와 `Retry-After` 로 답한다. 거절한 요청은 기준 시각을 밀지 않는다. 지금 CLI 는 `429` 를 재시도하지 않고 로그인을 실패시키므로, 정상 CLI 가 지터로 걸리지 않게 허용 오차를 둔다.
- 인증 URL(`verificationUrl`)의 기준 주소는 `API_BASE_URL` 설정이다. 없으면 요청의 Host 로 만든다. TLS 를 앞단에서 끝내는 운영에서는 설정해야 `https` 주소가 나온다.

## 결과
- 서버 재시작·replica 에서도 동작하고, 토큰을 한 번만 내주는 것이 DB 락으로 보장된다. DB 가 유출돼도 폴링 비밀과 토큰을 복원할 수 없다.
- CLI 로그인 흐름은 폴링마다 `last_polled_at` 을 쓰는 DB 쓰기 한 번을 감수한다(2초 간격, 최대 10분).
- 토큰을 내준 응답이 유실되면 복구할 수 없고 다시 로그인해야 한다(한 번만 내주는 것의 대가).
- 세션 JWT 는 ADR 0003 대로 만료 전 폐기할 수 없다. CLI 로그아웃은 저장한 토큰을 지우는 것뿐이다.
- 인증 URL 을 연 사람이 곧 승인자라서, 공격자가 만든 URL 을 피해자가 열어 승인하면 공격자의 CLI 가 피해자의 토큰을 받는다(Device Flow 와 같은 구조의 위험). 승인 전에 확인 화면을 두는 것은 계약 변경이라 이번에는 하지 않았다. 후속 과제다.
- 후속: iris-cli 가 `429`(`Retry-After`)를 기다린 뒤 재시도하게 하고, 운영 환경에 `API_BASE_URL` 을 설정하며, 달라진 점을 iris-cli 의 `docs/login-contract.md` 에 반영한다.
