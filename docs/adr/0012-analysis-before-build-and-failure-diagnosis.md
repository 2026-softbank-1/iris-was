# 0012. 분석·질문·계획을 빌드 전 단계로 보존하고 실패 로그 진단을 연결한다

- 상태: 제안됨
- 날짜: 2026-10-02
- 결정자: 개발팀 검토 대기

## 배경

단독 분석 결과와 배포 큐가 분리돼 원클릭에서 부족한 입력을 확인하거나 확정된 분석 계획을 실행할 수 없었다. WAS develop의 사용자/서비스 모델과 main의 기존 Worker 모델도 달랐다. 배포 전 분석은 사용자 분석 에이전트의 핵심 업무다.

## 결정

PipelineRun을 별도 영속 작업으로 접수한다. 고정 저장소 SHA→실제 분석기→원문 근거/부족 정보→사용자 입력→같은 분석기의 계획→검증된 플랫폼 BUILD/DEPLOY→실패 회차 진단을 연결한다. API는 접수와 사용자 권한을 담당하고 각 Worker는 모델·클라우드 실행 권한을 따로 가진다.

원본 분석과 portable dossier의 불확실성/실행 권한은 보존한다. 기존 운영 타깃의 Worker 계약을 별도로 만들고 분석 snapshot·result·입력·타깃 digest를 큐에서 재검사한다. Dockerfile을 쓰거나 고정 Railpack으로 빌드한다. 시작 명령이 없으면 이미지 기본값을 실행하고 실제 실패 로그를 진단한다. source/readiness/미지원 바인딩 문제는 빌드를 막는다.

실패 진단은 개발된 오류 에이전트의 v2 결과와 runtime을 고정 wheel로 재사용한다. 실제 로그의 출처·마스킹·제한을 저장하고 원래 배포 상태를 바꾸지 않는다. 수정 제안은 실행하지 않는다. 유료 실행 도중 복구가 불확실하면 동일 모델 호출을 반복하지 않는다.

## 결과

웹·WAS·두 에이전트의 API 및 worker 계획이 연결된다. 현재 ApplicationSet의 단일 AWS 타깃, 기존 namespace Secret 참조를 지원한다. 새로운 인프라 생성·빌드 단계 Secret provisioning·수동 역사 커밋 rollback은 별도 실행 계약이 필요하다. 실제 운영 적용에는 Worker 배포와 모델/AWS/GitOps 설정 및 iris-service chart 0.5.0 적용이 필요하다.
