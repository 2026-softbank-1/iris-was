# PR 본문 작성 스킬 (WAS)

작업 브랜치의 `develop` 대비 변경사항(릴리스 PR 은 `main` 대비)을 분석해, 이 프로젝트의 PR 템플릿 구조에 맞춰 `docs/PR.md` 로 **핵심만 간결하게** 작성하고, 변경에 맞춰 README.md·CLAUDE.md 를 동기화한다.

> 실제 GitHub PR(`gh pr create`)은 생성하지 않는다. 본문 문서와 문서 동기화 커밋만 만든다 — 푸시·PR 생성은 사용자가 직접 한다.

---

## 작업 절차

### Step 1: 상태 확인

```bash
git rev-parse --show-toplevel   # git 레포 아니면 중단
git branch --show-current
git status --short
git diff develop...HEAD --stat
```

- git 레포가 아니면 중단.
- 현재 브랜치가 `main`·`develop` 이면 중단하고 새 브랜치 생성 여부를 사용자에게 확인.
- `develop` 대비 변경(diff/커밋)이 없으면 중단하고 보고.

### Step 2: 변경 내용 분석

```bash
git log develop..HEAD --oneline
git diff develop...HEAD --stat
```

- 커밋 메시지와 변경 파일로 **무엇을·왜** 바꿨는지 파악한다.
- 핵심이 불명확하면 주요 파일의 diff(`git diff develop...HEAD -- <file>`)를 읽어 보강한다.
- **코드 워크플로우**를 그릴 수 있도록, 변경된 흐름의 진입점(엔트리)과 그 흐름을 처리하는 public 함수·메서드를 식별한다.

### Step 3: 템플릿 구조 읽기

```bash
cat .github/PULL_REQUEST_TEMPLATE.md
```

- **항상 현재 템플릿을 읽어** 섹션 제목·순서를 그대로 따른다(템플릿이 바뀌어도 동기화 유지). 섹션을 임의로 추가·삭제하지 않는다.
- 현재 템플릿 섹션: `🎯 목적` / `📝 작업 요약` / `✅ 체크리스트` / `📌 기타`.

### Step 4: `docs/PR.md` 작성

- `docs/` 가 없으면 생성. 파일은 `docs/PR.md` 고정, 있으면 덮어쓴다.
- 맨 위에 PR 제목(70자 이내, 한국어) 1줄, 그 아래 템플릿 섹션을 채운다.
- 📝 작업 요약 안에는 **코드 워크플로우(ASCII 다이어그램)**를 하위 항목으로 넣는다.
- ✅ 체크리스트는 **리뷰어가 중점적으로 봐줬으면 하는 부분**만 `- [ ]` 체크 항목으로 적는다.
- 템플릿의 `<!-- 주석 -->` 가이드 문구는 결과물에 남기지 않는다.

````markdown
# {PR 제목 (70자 이내, 한국어)}

## 🎯 목적

{이 PR 이 왜 필요한지 1~2문장}

## 📝 작업 요약

- {핵심 변경 1}
- {핵심 변경 2}

### 코드 워크플로우

```text
[입력 동작을 일상 언어로 한 문장]
   ↳ module.public_function()
              │
              ▼
[다음 처리를 일상 언어로]
   ↳ module.public_function()  (외부: ...)
              │
       ┌─ {조건} ─▶ [분기 A 동작]
       │              ↳ module.public_function()
       └─ {조건} ──▶ [분기 B 동작]
                      ↳ module.public_function()
```

## ✅ 체크리스트

- [ ] {리뷰어가 중점적으로 봐줬으면 하는 부분·논의점 1}
- [ ] {봐줬으면 하는 부분 2}

## 📌 기타

{영향 범위·롤백 방법·스크린샷 등. 없으면 섹션 생략}
````

> `코드 워크플로우` 는 PR 템플릿의 별도 섹션이 아니라 **📝 작업 요약 안의 하위 항목**이다(Step 3 의 "템플릿 섹션 임의 추가 금지"와 충돌하지 않음).

### Step 5: 문서 동기화 (README.md / CLAUDE.md)

현재 README.md·CLAUDE.md 를 읽고, 이번 변경에 맞춰 갱신이 필요한지 판단해 **있는 내용만 최소로** 반영한다. 없는 섹션을 새로 만들거나 기존 내용을 왜곡하지 않는다.

**README.md 갱신 대상**

| 변경 유형 | 반영 위치 |
|---|---|
| 새 API 엔드포인트 | API 목록 / 사용법 |
| 새 기능·도메인 | 기능 목록 |
| 실행 방법 변경 | Getting Started / 자주 쓰는 명령 |
| 새 환경변수 | 환경변수 설정 |
| 의존성 변경 | 기술 스택 |

**CLAUDE.md 갱신 대상**

| 변경 유형 | 반영 위치 |
|---|---|
| 새 아키텍처 레이어·패턴 | 핵심 원칙 / 규칙 문서 표 |
| 새 커맨드·스크립트 | 도구 |
| 새 도메인 모델·상태 | (용어 사전과 연계) |
| 새 패키지 구조 | 레이어 경계 |
| 새 기술 스택·라이브러리 | 스택 |

**갱신 불필요**: 내부 리팩토링만 / 테스트 코드만 변경 / 이미 문서에 반영됨 → 건너뛴다.

**커밋** — README.md·CLAUDE.md 가 실제로 바뀐 경우에만 커밋한다. 커밋 메시지는 [git-conventions.md](../../rules/git-conventions.md) 를 따른다(`docs: ...`).

```bash
# README/CLAUDE.md 만 스테이징 — docs/PR.md 는 커밋하지 않는다
git add README.md CLAUDE.md
git commit -m "docs: README·CLAUDE.md 동기화"
```

- **`docs/PR.md` 는 커밋하지 않는다.** 코드 변경은 이미 커밋돼 있어야 한다.
- 바뀐 문서가 하나도 없으면 커밋을 **생략**한다(빈 커밋 금지).

---

## 작성 규칙

- **간결성 최우선.** 각 섹션은 핵심만. 장황한 설명·중복·인사말 금지.
- 🎯 목적: 1~2문장. 배경/이유 중심(무엇을 했는지가 아니라 왜).
- 📝 작업 요약: bullet 3~7개. 커밋 단위가 아니라 **의미 단위**로 묶는다.
- ✅ 체크리스트: `- [ ]` 체크 항목 1~5개. **리뷰어가 중점적으로 봐줬으면 하는 부분·논의점만** 적는다. 없으면 `- [ ] 특이사항 없음` 한 줄.
- 📌 기타: 영향 범위·롤백·스크린샷 등 **실제 해당될 때만**. 없으면 섹션 자체를 뺀다.
- 언어는 한국어. 도메인 용어는 [term-dictionary.md](../../rules/term-dictionary.md) 표준 영문어를 따른다.

### 코드 워크플로우 규칙

- 코드 블록(```text)으로 감싸 고정폭 정렬을 보장한다.
- 각 단계는 **두 줄 한 쌍**으로 적는다.
  - 1줄: `[비즈니스 동작을 일상 언어로 한 문장]` — 도메인 용어는 풀어 쓰고 무엇이 일어나는지를 서술한다. **함수·메서드 이름을 1줄에 넣지 않는다.**
  - 2줄: `   ↳ module.public_function()` — 그 단계를 처리하는 public 함수/메서드. 여러 개면 줄을 나눠 `↳` 로 각각 나열한다.
- 흐름은 `──▶`·`│`·`▼`, 분기는 `┌─ {조건} ─▶` / `└─ {조건} ──▶` 처럼 **한국어 라벨**을 단다.
- 외부 호출·이벤트는 `(외부: GitHub API)`, `(이벤트: ...)` 처럼 괄호 한국어 라벨로 표기한다.
- private/internal helper 는 넣지 않고 **호출 경로의 표지가 되는 public 함수만** 적는다.
- 단순 리팩토링·문서 수정이라 흐름 변화가 없으면 다이어그램 대신 **"흐름 변화 없음"** 한 줄만 적는다.

## 완료 보고

```
✅ PR 본문 작성 완료 — docs/PR.md
   문서 동기화 — README.md: {수정됨/변경 없음} · CLAUDE.md: {수정됨/변경 없음}

## 핵심 작업 사항
- {기술적으로 중요한 변경 1}
- {변경 2}
```

핵심 작업 사항은 중요한 변경만 1~5줄 bullet 으로 요약한다.
